## Что делаем

1) Новый шов /api/parse (backend, отдельный роутер, ДО фазы 1)
   Вход:  { "text": "<фраза>", "radius_km"?: int }
   Выход: { "ingredients": [str], "radius_km": int, "unmatched": [str] }
   - LLM (по умолчанию Claude Haiku 4.5 — дёшево/быстро для structured extraction)
     маппит фразу на РАЗРЕШЁННЫЙ словарь ингредиентов. Список ингредиентов и их
     русские синонимы даём модели в промпте ИЗ ingredients.yaml — единый источник,
     не хардкодить второй список.
   - Ноль вызовов Tutu. Это pre-фаза-1, сеть только к модели.
   - Выход ОБЯЗАН пройти тот же _validate, что ручной ввод (unknown → выкинуть в
     unmatched, не в ingredients). Модель не может протащить мусор в ядро.
   - Радиус: если пользователь сказал «недалеко/рядом» → 50/100, иначе default.
     Только из ALLOWED_RADIUS_KM.

2) Фолбэк (обязателен, иначе инвариант нарушен)

# Заметка надзора (не в лаунчер)

- Приоритет: делать **только вход**. «Выход-питч» (карточка → текст) — почти
  бесплатный бонус, но отдельным нарядом и только при запасе времени. 80% вау
  даёт именно вход.
- Риск-профиль низкий: выход модели зажат существующим `_validate` (guard уже
  отбивает unknown ингредиент и радиус не из `{50,100,150}` → 400). LLM физически
  не пробивает контракт ядра.
- Единственный новый внешний ключ в проекте — к модели, и он **опционален по
  дизайну**. Это сознательно: чтобы AI-вход не стал ещё одним блокером боевого
  запуска рядом с живым Tutu (см. вопрос про G-live).
- Проверка после сдачи: убедиться, что путь эталона и путь `/api/parse` не
  делят код — иначе инвариант `etalon-bypasses-llm` формально соблюдён, а
  фактически нарушен.
