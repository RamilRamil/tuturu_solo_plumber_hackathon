# Stream D — фронт

Пользователь собирает «бургер» из типов интересов → видит карту мест **без origin и без цен** → затем вводит origin, даты и состав и достраивает маршрут ценами по мере событий SSE.
**Инверсия: направление — выход системы, а не вход.** Origin не спрашивают, пока нет мест.

Тонкая спека: субстанция контракта и приёмки уже заморожена. Здесь — поведение экрана потока D и швы, которые D обязан соблюдать. Не копировать [mvp-spec.md](../../mvp-spec.md) §4/§5/§12.

Приоритет источников: `schema.sql` > [plans/api-contract.md](../../plans/api-contract.md) > [plans/00-orchestration.md](../../plans/00-orchestration.md) §0 > `mvp-spec.md`.

## Границы потока D в 001

**Входит**

- Меню ингредиентов с обязательной меткой плотности.
- Дискретный ползунок радиуса 50 / 100 / 150 км (верх 150, дефолт 100).
- Фаза 1: карта + карточки топ-5 **без цен и без бюджета**.
- Фаза 2: origin / даты / состав → поток цен по мере событий; раскладка обязательна.
- Серые карточки с причиной; пометка «дальше своим ходом» у непродаваемых узлов.
- Блок «почти подходит» (неполное покрытие бургера).
- Карта покрытия данных: честная дыра (V4).
- Три состояния часов объекта. Шеринг-ссылка после G10 (часы 40–44).

**Не входит в 001 / не работа D**

- Полноценный веб-поиск часов работы (кандидат 002+; F4 режется первым).
- LLM-матчинг свободного «другое» как обязательный путь (F3/F5: без LLM поле можно отключить).
- Покрытие всей России, аккаунты, платежи.
- Кластеризация, ингест, живой Tutu MCP — потоки B / A / C.
- Резать пары городов (B4 запрещает). Чужой сайт / чужой домен как край продукта.

## User Scenarios & Testing

### User Story 1 — Собрать бургер и увидеть места без origin (Priority: P1)

Как путешественник, я выбираю типы интересов и радиус и сразу вижу, **где в России они сосуществуют**, ещё не называя город выезда.

**Why this priority:** это инверсия продукта; без фазы 1 нет G10.

**Independent Test:** на моках эталона №1, без поля origin, выдаётся карта и топ карточек.

**Acceptance Scenarios:**

1. **Given** меню ингредиентов, **When** пользователь смотрит карточки, **Then** у каждой видна метка `density_label` (`dense` / `medium` / `rare` / `absent_in_region`); при известном замере рядом может быть число (храмы 370, водопады 0).
2. **Given** выбран `ancient_temple` + `industrial_museum` и радиус 100, **When** запрос фазы 1 успешен, **Then** эталон «Ярославль и Ростов Великий» в **видимом топ-5** (не обязан быть первым: одиночный Ярославль с тем же покрытием законен); цен и бюджета на карточках нет. Для фазы 2 пользователь/скрипт демо **выбирает карточку пары**.
3. **Given** выбран `ancient_temple` + `ruins` и радиус 100, **When** запрос фазы 1 успешен, **Then** запасной одноузловой кластер Ярославля в **видимом топ-5**.
4. **Given** ползунок радиуса, **When** пользователь двигает его, **Then** доступны только защёлки 50, 100, 150; значение > 150 недоступно; дефолт 100; на каждом шаге виден счётчик найденных мест (`total_found`).

### User Story 2 — Origin и цены по мере готовности (Priority: P1)

Как путешественник, я называю origin, даты и состав **после** карты мест и вижу маршрут и деньги постепенно, а не после долгого спиннера.

**Why this priority:** критерий G10 (конец часа 26) — выбранная карточка пары в топе фазы 1 и в потоке фазы 2 (не обязательно `places[0]`).

**Independent Test:** `cluster_id` выбранной карточки пары открывает поток цен; события приходят по одному.

**Acceptance Scenarios:**

1. **Given** в топ-5 есть карточка эталона-пары, **When** пользователь вводит origin Москва, 3 дня, месяц `2026-10`, 1 взрослый, **Then** поток идёт по **тому же** `cluster_id`, что у **выбранной** карточки пары (`c:Ростов|Ярославская область,Ярославль|Ярославская область`), даже если в списке выше стоит одиночный Ярославль.
2. **Given** открыт поток цен, **When** приходят события, **Then** UI рисует их по мере поступления (`resolved`, `leg`, `hotel`, `breakdown`, `checkout`, `warning`, `done`), не дожидаясь пачки в конце.
3. **Given** показана хотя бы одна цена, **When** поток завершается, **Then** видна раскладка `breakdown` (транспорт / жильё / итого) до или вместе с `done`; без раскладки итог не считается готовым.
4. **Given** событие `checkout`, **When** пользователь жмёт оформление, **Then** открывается `checkout_url` **как пришёл**, без сборки, обрезки и подмены хоста.
5. **Given** нет живого прогона Tutu по **обоим** сценариям, **When** виден итог, **Then** статус цены — `fixture-confirmed` (в карточке и/или отчёте). Снимать метку только после живого прогона эталона **и** запасного бургера.

### User Story 3 — Серые карточки и «почти подходит» (Priority: P2)

Как путешественник, я не теряю найденные места после origin: недостижимые сереют с причиной; неполное покрытие бургера лежит отдельно.

**Why this priority:** тихий отказ «карточка пропала» ломает демо (orchestration §7).

**Independent Test:** после origin список не укорачивается за счёт удаления; меняется оформление.

**Acceptance Scenarios:**

1. **Given** места фазы 1, **When** origin делает часть кластеров недостижимой, **Then** карточки **остаются**, сереют, показывают причину; не удаляются.
2. **Given** узел `probe_status=not_sellable`, **When** карточка на экране, **Then** пометка «дальше своим ходом»; карточка остаётся.
3. **Given** кластер с непустым `coverage.missing`, **When** выдача построена, **Then** он в блоке «почти подходит», не смешан с полным покрытием.
4. **Given** пожар по таймлайну (B4), **When** режут объём, **Then** блок «почти подходит» режется **первым**; пары и эталон №1 не режутся.

### User Story 4 — Честная дыра покрытия (Priority: P2)

Как жюри (и как пользователь с origin вне залитых областей), я вижу, **куда данные ещё не доехали**, а не пустую выдачу как «таких мест нет».

**Why this priority:** V4; скрытая дыра читается как поломка продукта.

**Independent Test:** на карте покрытия залитые регионы отделены от пустых штриховкой/подписью.

**Acceptance Scenarios:**

1. **Given** список залитых регионов от A (D3), **When** открыта карта покрытия, **Then** видно «данные загружены по N областям»; регионы без данных — штриховка или эквивалент «дыры».
2. **Given** origin в незалитом регионе, **When** фаза 1 пуста или бедна, **Then** UI не выдаёт это за отсутствие ингредиентов; дыра названа этапом загрузки.

### User Story 5 — Часы объекта (Priority: P3)

Как путешественник, я вижу честный статус часов, а не «закрыто», если тега нет.

**Acceptance Scenarios:**

1. **Given** объект, **When** показан статус, **Then** одно из трёх: открыт / закрыт / неизвестно (`hours_status`: `open` / `closed` / `unknown`).
2. **Given** `opening_hours` пуст (типичные 88%), **When** карточка объекта, **Then** статус `unknown`, не `closed`.
3. **Given** границы 001, **When** пользователь ждёт полный веб-поиск часов, **Then** этого полного сценария в 001 нет (ленивый клик — F4, фолбэк «режется»).

## Edge Cases

- Пустой список ингредиентов — запрос фазы 1 не уходит; контракт: 400.
- Радиус вне {50, 100, 150} — UI не предлагает; контракт: 400.
- Два `rare` / `absent_in_region` — меню уже предупредило плотностью; пустая выдача или «почти подходит» допустимы, это не поломка.
- Неизвестный `cluster_id` на цене — 404, не событие `warning` в SSE.
- Цена плеча 0 — отсутствие тарифа, не «0 ₽».
- `hotel.min_price` — `stay_total` за пребывание; UI не умножает на `nights`.
- `guard=misresolved` не подменяется на `not_sellable`.
- Смена радиуса при том же множестве хабов **не** меняет `cluster_id` (ключ шеринга).
- Кэш-фолбэк фазы 2 — показать с пометкой источника/времени, не как свежий live без метки.

## Functional Requirements

- **FR-D1.** Меню показывает ~20 карточек из [ingredients.yaml](../../ingredients.yaml) плюс поле «другое» с подсказками. Пока нет детерминированного матчинга (F5), «другое» можно отключить, не ломая остальной поток.
- **FR-D2.** На каждой карточке ингредиента **обязательна** видимая метка плотности `density_label`. Скрытая плотность = дефект: пользователь соберёт несуществующую комбинацию.
- **FR-D3.** Ползунок радиуса — дискретные шаги 50 / 100 / 150 с защёлкой, максимум 150 км (порог D2), дефолт 100. Свободный непрерывный ползунок запрещён (V2).
- **FR-D4.** Фаза 1 не показывает цены, бюджет, `breakdown` и оформление. Бюджет появляется только после origin в фазе 2.
- **FR-D5.** Карта и карточки рядом. На карте — объекты выбранного кластера; в карточке топа — хабы, фактический диаметр (`diameter_km`, подпись честная, F17), `coverage.matched` / `coverage.missing`, редкость, объекты.
- **FR-D6.** Топ выдачи фазы 1 — до 5 карточек полного покрытия по сортировке B3 (UI не переранжирует). SC-ranking проверяется **в UI** теми же фикстурами, что и бэкенд.
- **FR-D7.** Фаза 2 запрашивает цену по `cluster_id` карточки. Поля: origin, число дней в месяце, `adults`, `children_ages`, `budget_scope` (`transport` по умолчанию, переключатель `all`).
- **FR-D8.** События SSE рендерятся инкрементально. Пачка в конце (как будто прокси сбуферизовал) — дефект G6 для UX, даже если JSON верен.
- **FR-D9.** Раскладка по категориям обязательна, если была показана цена. Кнопка оформления использует `checkout_url` без изменения.
- **FR-D10.** Недостижимые после origin карточки не исчезают — серые с причиной. Непродаваемый узел — «дальше своим ходом».
- **FR-D11.** «Почти подходит» — отдельный блок неполного `coverage`. При пожаре B4 этот блок режется первым.
- **FR-D12.** Карта покрытия: залитые области явно, незалитые — дыра, не маскировка. Список регионов — от A (D3), не выдуманный фронтом.
- **FR-D13.** Часы объекта — три состояния; отсутствие тега = неизвестно.
- **FR-D14.** G10 (конец часа 26): пользователь на одном `cluster_id` видит топ `POST /api/places` и поток `POST /api/price` (`resolved` + хотя бы один `leg` + `done` по одному, не пачкой).
- **FR-D15.** Пока нет живого Tutu по эталону **и** запасному бургеру, UI помечает цену `fixture-confirmed`. Итог 4 342 ₽ из фикстуры не выдавать за живой SC-price.
- **FR-D16.** Шеринг (после G10): ссылка несёт бургер + origin + даты + тот же `cluster_id`. Смена только радиуса без смены множества хабов не чеканит новый id.
- **FR-D17.** Переключатель `mock` / `live` на старте. Моки совпадают с контрактом, не с устаревшим примером `yar-rostov` из mvp-spec §4.

## Key Entities

| Сущность | Смысл для UI |
|---|---|
| Burger | Набор id ингредиентов + `radius_km`. Origin не часть бургера. |
| Ingredient | Карточка меню; `density_label` обязателен. |
| Place / cluster | Место на карте; идентичность = `cluster_id` (множество `hub.id`, радиус не в id). |
| Hub | Узел карточки; `probe_status` ∈ {`sellable`, `not_sellable`, `misresolved`}. |
| Coverage | `matched` / `missing`; дырка → «почти подходит». |
| Price stream | Последовательность SSE-событий по тому же `cluster_id`. |
| Coverage map | Залитые vs незалитые регионы (честная дыра). |
| Hours | `open` / `closed` / `unknown`. |

## Success Criteria

- **SC-D1.** Без origin пользователь за один заход видит карту мест и топ до 5 карточек **без цен**.
- **SC-D2.** Эталон №1 (`ancient_temple` + `industrial_museum`, 100 км): карточка пары Ярославль+Ростов занимает место в видимом топ-5 на фикстурах (не обязательно первое). Одиночный Ярославль с полным покрытием законен. Демо кликает пару. (SC-ranking в UI).
- **SC-D3.** Запасной бургер (`ancient_temple` + `ruins`, 100 км) занимает место в видимом топ-5 на своём запросе (SC-ranking в UI).
- **SC-D4.** К концу часа 26 (G10) на одном `cluster_id` эталона пользователь видит топ фазы 1 и инкрементальный поток фазы 2: `resolved`, хотя бы один `leg`, `done` — с заметными паузами, не единой пачкой.
- **SC-D5.** 100% карточек ингредиентов в меню несут видимую плотность; ползунок не позволяет радиус выше 150 км.
- **SC-D6.** После origin число карточек не падает за счёт удаления: недостижимые остаются серыми с причиной.
- **SC-D7.** Карта покрытия позволяет отличить «регион не залит» от «комбинации нет» без пояснений разработчика (жюри смотрит само).
- **SC-D8.** Итог цены в UI помечен `fixture-confirmed`, пока не было живого прогона Tutu для обоих сценариев. `checkout_url` совпадает с событием `checkout` посимвольно.

## Assumptions

- Контракт [plans/api-contract.md](../../plans/api-contract.md) заморожен (G2). Отдельного эндпоинта меню в контракте нет: словарь плотности — [ingredients.yaml](../../ingredients.yaml) (локально / тот же мок-каталог).

- G6 зелёный: SSE через nginx `:8080` приходит по событиям. Фронт не включает буферизацию ответа на своей стороне.
- CORS на G10: один origin через nginx-прокси (F10). Локалка — compose на `:80`; демо-край — `:8080`.
- Стек заморожен G8, не выбирается в этой спеке: React 18 + Vite + TypeScript + MapLibre (**не** Leaflet), npm, Node 20. D владеет приложением.
- Комбо запасного бургера в UI = `ancient_temple` + `ruins` (F13), пока B не скажет иначе.
- Окна дат в месяце считаются лениво (V3); первый `leg` ожидаем порядка ~3 с, не после всех плеч.
- Полноценный веб-поиск часов и LLM «другое» не блокируют приёмку G10.
