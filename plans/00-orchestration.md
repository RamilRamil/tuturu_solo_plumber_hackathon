# Оркестрация: «Бургер» — план параллельной разработки

Мастер-документ. Кто что делает, в каком порядке, где швы между потоками.
Продуктовые решения и блокеры зафиксированы ниже — работать по ним, не переоткрывать.

Роли: **Оркестратор** (координация, этот документ), **Архитектор** (целостность,
схема БД, контракты, ревью швов), **Рабочие A/B/C/D** (потоки ниже).

---

## 0. Зафиксированные решения (не переоткрывать)

- **B1.** Три исхода пробы: `SELLABLE` / `NOT_SELLABLE` / `MISRESOLVED`. Таблица
  алиасов `data/city_aliases.json`. Стратегия — ретрай по вариантам имени
  (алиас → имя как есть → «имя, субъект»), а не отказ. Регресс-тест на ингест.
- **B2.** Продаваемость перегона — свойство **ребра**. Таблица `leg` (направленная
  пара). `hub.sellable_modes` переименовать в производное `reachable_from_any`.
- **B3.** Функция ранжирования кластеров определена (см. `plans/worker-B-phase1.md`).
  `coverage_ratio` доминирует.
- **B4 → РЕШЕНИЕ: «держим оба».** Пары городов объявлены **нерезаемыми**.
  Эталон №1 (Ярославль→Ростов Великий, `ancient_temple` + `industrial_museum`)
  остаётся основным. Не `industrial_site` / заводы: честный слой — музеи
  промышленности (`ingredients.yaml`, ингест A). Фейковые `industrial_site`-POI
  не добавлять. Дополнительно поддерживается **запасной одноузловой бургер**
  (`ancient_temple` + `ruins`/`spring`), выживающий на одном узле — на случай
  пожара по таймлайну. Оба сценария входят в регресс-тест приёмки.
  Cut-list меняется: режем сначала «почти подходит» и часть блоков фазы 2,
  пары — в последнюю очередь.
- **Эталон: coverage-честность (2026-08-19, не переоткрывать).** В золотых
  `poi` Ярославль несёт оба ингредиента эталона; одиночный Ярославль — законный
  полный ответ (coverage=2). Не вырезать `ancient_temple` у Ярославля (волна 1
  OSM вернёт храмы). Не калибровать `w1..w6`, чтобы пара стала #1. Скрипт демо
  кликает пару для фазы 2 по `cluster_id` из `fixtures/etalon_1.json`, не
  `places[0]`. Регресс — живой проход дисков; после `load_golden_fixtures`
  таблица `cluster` пуста (`DELETE FROM cluster`).
- **Эталон: SC-B1 structural + smoke (2026-08-19, не переоткрывать).**
  «Пара в топ-5» — smoke на золотых фикстурах, не pass/fail сборки и не
  обещание после волны 1 (геометрия соседей сменится). Жёсткий SC-B1: в
  `places[]` есть кластер с обоими хабами эталона и `coverage.matched` = оба
  ингредиента, `missing` пуст. Жёсткий SC-B2: есть одноузловой Ярославль с
  полным покрытием запасного бургера. Плюс SC-B3 (монотонность coverage).
  `rarity.total_places_with_combo` — честный счётчик кластеров с тем же
  `matched`; на этом бургере это не вау «редкая связка». Вау редкости — только
  на комплементарном бургере (ни один узел не несёт оба ингредиента); в 001
  такого нет, на G10 не обещать.

Продуктовые константы из mvp-spec §10 действуют как есть.

## 1. Карта потоков и зависимостей

```
STREAM 0 — Фундамент (Архитектор + Оркестратор), час 0–3, КРИТИЧЕСКИЙ ПУТЬ
  репо-скелет, схема БД (с leg + 3 исхода), контракт API (фикс),
  общий MCP-клиент как lib, фикстуры, регресс-тесты приёмки (пустые)
        │
        ├──────────────┬───────────────┬────────────────┐
        ▼              ▼               ▼                ▼
  STREAM A         STREAM B        STREAM C         STREAM D
  Ингест (VPS)     Фаза 1          Фаза 2           Фронт
  (долгий, фон)    (локальная)     (Tutu live)      (React+Map)
```

Зависимости (жёсткие):

| Зависимость | От кого | Кому | Обход на старте |
|---|---|---|---|
| Схема БД | Stream 0 | A, B, C | — (час 0–1, блокер) |
| Контракт API | Stream 0 | B, D | §4 mvp-spec уже почти финал |
| MCP-клиент (lib) | Stream 0 | A, C | общий модуль, не дублировать |
| Реестр узлов (D1) | A1 | B (флаг sellable), C, A4 | фикстуры узлов |
| POI (D3) | A2 | B (кластеры) | фикстуры POI по Ярославской обл. |
| Матрица перегонов (D2) | A4 (нужен A1) | B (серые карточки), C | фикстуры leg |

**Ключ к параллельности:** B, C, D стартуют на **фикстурах**, не дожидаясь
ингеста. Stream 0 обязан выдать фикстуры в первые 2 часа. Реальные данные из
A подменяют фикстуры позже без изменения кода.

## 2. Что делает каждый поток (одна строка)

- **Stream 0 / Архитектор** — скелет, схема, контракт, MCP-lib, фикстуры, CI-регресс.
- **Stream A / Ингест** — реестр узлов (D1), POI из OSM (D3), Wikidata (D4),
  матрица перегонов (D2), прогрев кэша (D5). Живёт в `ingest/`, крутится на VPS.
- **Stream B / Фаза 1** — кластеризация §6 (диски вокруг узлов), `/api/places`,
  скоринг significance §9, ранжирование кластеров B3, счётчик редкости. Без сети.
- **Stream C / Фаза 2** — `/api/price` по SSE: legs, hotel, breakdown, checkout,
  guard §7, кэш и фолбэк-режим, обратные плечи.
- **Stream D / Фронт** — бургер-меню с плотностью, ползунок радиуса (дискретный),
  карта MapLibre + карточки, потребление SSE, серые карточки, «почти подходит»,
  карта покрытия данных.

Детали — в `plans/worker-*.md` и `plans/architect.md`.

**После G9 → раздать планы B/C/D.** G9 (золотые фикстуры) разблокирует параллельность.
Не открывать код кластеризации, `/api/places`, `/api/price` и фронт, пока оркестратор
не раздал `plans/worker-B-phase1.md`, `plans/worker-C-phase2.md`,
`plans/worker-D-frontend.md`. Каждый субагент ведёт свой поток по **Spec Kit**
в OKF-бандле (`specs/001-burger-mvp/`: один концепт = один markdown, YAML frontmatter,
путь файла = идентичность; формат —
[Open Knowledge Format](https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing)).
Стоп после своей спеки — контроль оркестратора. Plan / tasks / implement не начинать
без зелёного. Старт исполнения — на фикстурах (эталон №1 + запасной одноузловой
бургер), не на живом ингесте A.

**G10. Ранний интеграционный чекпоинт — конец часа 26.** Владелец: архитектор + оркестратор.
Не ждать часа 44. Кандидат сборки всех четырёх (A+B+C+D): конец часа 26 —
первый сквозной вызов `/places` → `/price`.

Критерий (сборка не валится по SC-price):

1. эталон №1: в `POST /api/places` **существует** кластер пары Ярославль+Ростов
   с полным покрытием + SC-B3 — **SC-ranking hard** (офлайн; одиночный
   Ярославль с тем же coverage законен; прогон с пустой `cluster`). «Пара в
   топ-5» — smoke на фикстурах, не валит G10 и не требуется после волны 1;
2. запасной одноузловой бургер: **существует** одноузловой Ярославль с полным
   покрытием — **SC-ranking hard**; «в топ-5» — smoke на фикстурах;
3. `POST /api/price` по тому же `cluster_id`: события `resolved` + хотя бы один `leg` + `done` приходят **по одному** (G6), не пачкой;
4. цена в UI/отчёте помечена `fixture-confirmed`, пока не было живого прогона Tutu для обоих сценариев.

Критерий потока A на чекпоинте: волна 1 (D1+D3) готова к подмене золотых `fixtures/`.

Часы 44–48 остаются живой **SC-price** и репетицией демо, не первой сборкой.

**Что режем первым при пожаре (после B4):** «почти подходит» → часть блоков
фазы 2 → отели. **Пары не режем.**

## 4. Швы, за которые отвечает Архитектор

1. **Схема БД** — единственный источник, все потоки импортируют модели, не
   определяют свои. Особо: таблица `leg` (B2), три исхода в пробере (B1).
2. **Контракт API** (`/api/places`, `/api/price` SSE) — заморозить до старта B и D.
   Любое изменение — через Архитектора, с уведомлением D.
3. **MCP-клиент** — один модуль `lib/tutu_mcp.py`, используют A и C. Guard §7 —
   там же, не копировать в два места.
4. **Фикстуры** — золотой набор для регресса приёмки (эталон №1 + запасной бургер).

## 7. Тихие отказы, которые ломают демо (держать под контролем везде)

- Мисрезолв возвращает нормальную выдачу с ценами → guard обязателен до цены.
- Per-mode soft-fail молчит → сверять `modes_requested` с `modes_summary`.
- Цена отеля = `stay_total`, не за ночь → не умножать на nights.
- «Нет тега opening_hours = закрыт» отсечёт 88% → трёхзначная логика часов.
- Непродаваемые узлы не удалять → режим «дальше своим ходом».
- Недостижимые после origin не исчезают → серые с причиной.
