# ТЗ на MVP: «Бургер» — конструктор путешествия

Читать вместе с `tutu-mcp-reference.md` (справочник по API) и `tutu-mcp-field-test.md` (полевая проверка, все числа ниже оттуда).

---

## 1. Что строим

Пользователь не знает, куда хочет ехать. Он собирает «бургер» из типов интересов («промышленный туризм» + «древний храм»). Система находит места в России, где эти типы сосуществуют в пределах заданного радиуса, и только потом спрашивает город отправления — после чего достраивает маршрут, цены и ссылки на оформление через Tutu MCP.

**Ключевая инверсия:** направление — это выход системы, а не вход.

---

## 2. Жёсткие ограничения (проверено живьём)

1. **Малые города Tutu не продаёт.** Выкса, Суздаль, Кириллов, Городец резолвятся в гео, но не имеют `avia_id`/`railway_id`, а автобус и электричка дают ноль. Нужен эмпирический реестр продаваемых узлов.
2. **Резолвинг городов молча врёт.** «Великий Новгород» → Санкт-Петербург, «Ростов» → Ростов-на-Дону. `also_named` не приходит ни разу. Обязателен guard (§7).
3. **`tutu://geo` — пустышка.** 2 города, 30 остановок, поля только `geo_id` и `name`. Координат нет. Справочник строим сами.
4. **Латентность Tutu: 0,7–26,7 с**, медиана ≈ 3 с. Синхронный UX невозможен, только стриминг.
5. **Составные маршруты не строятся.** Торжок → Москва = 0, хотя через Тверь доехать можно. Обратное плечо проверять отдельным вызовом.
6. **Публичный Overpass не выдержит нагрузки.** Дамп OSM берём с Geofabrik и парсим локально через pyosmium.

---

## 3. Архитектура: две фазы

```
ФАЗА 1 (локальная, мгновенная, без Tutu)
  бургер + радиус → кластеры мест → карта + карточки без цен

ФАЗА 2 (живая, стриминг, Tutu MCP)
  + origin + даты + состав → маршруты, цены, чекаут
```

Граница между фазами — главное архитектурное решение. В фазе 1 нет ни одного сетевого вызова наружу. В фазе 2 дорогие вызовы идут только для топ-5 кластеров.

**Следствие для UI:** в фазе 1 бюджет неприменим (цен ещё нет), а после ввода origin часть найденных мест окажется недостижимой. Такие карточки **не исчезают, а сереют с причиной**.

```jsonc
               "lat": 57.626, "lon": 39.887, "sellable": true }],
    "center": { "lat": 57.4, "lon": 39.6 },
    "diameter_km": 58,
    "coverage": { "matched": ["ancient_temple", "industrial_museum"], "missing": [] },
    "rarity": { "rank": 3, "total_places_with_combo": 7 },
    "objects": [{
      "id": "n123", "name": "Церковь Воскресения Христова",
      "ingredient": "ancient_temple", "lat": 57.18, "lon": 39.41,
      "significance": 7, "wikidata": "Q123",
      "start_date": { "raw": "1670", "from": 1670, "to": 1670 },
      "opening_hours": null, "hours_status": "unknown"
    }]
  }]
}
```

### `POST /api/price` — фаза 2, ответ по SSE

```jsonc
{ "cluster_id": "yar-rostov", "origin": "Москва",
  "days": 3, "month": "2026-10",
  "adults": 2, "children_ages": [8],
  "budget_scope": "transport" }   // "transport" | "all"
```

| event | payload |
|---|---|
| `resolved` | что резолвилось, результат guard'а (§7) |
| `leg` | одно плечо: from, to, mode, price, duration, checkout_ref |
| `hotel` | город, min_price, nights, checkout_ref |
| `breakdown` | раскладка по категориям: транспорт / жильё / итого |
| `checkout` | готовые `checkout_url` по каждому плечу |
| `warning` | плечо не найдено, объект без часов работы и т. п. |
| `done` | финальный итог |

Раскладка по категориям обязательна.

## 5. Схема данных (SQLite)

```sql
poi(id, osm_type, osm_id, lat, lon, name, ingredient_id,
    wikidata, wikipedia, start_date_raw, start_date_from, start_date_to,
    opening_hours, significance, tags_json)

hub(id, name, region, lat, lon, tutu_geo_id,
    sellable_modes,        -- 'railway,bus,etrain' или ''
    checked_at)

cluster(id, hub_ids, center_lat, center_lon, diameter_km, ingredient_mask)

route_cache(origin_hub, dest_hub, date, payload_json, fetched_at)
hotel_cache(hub_id, check_in, check_out, adults, payload_json, fetched_at)
misresolve_log(requested, got_name, got_region, expected_region, at)
```

`route_cache` и `hotel_cache` — они же фолбэк для демо.

## 6. Кластеризация — НЕ DBSCAN

Пользователь понимает радиус как **диаметр набора**: все объекты не дальше N км друг от друга. Плотностная кластеризация даёт связность через цепочку и на радиусе 100 км склеит пол-страны в один кластер.

**Алгоритм:**

1. Кандидат кластера — один продаваемый узел или **пара** узлов на расстоянии ≤ `radius_km`.
2. POI кластера — объекты в радиусе `r_local` (дефолт 25 км) от любого из узлов.
3. Диаметр считаем фактический, по крайним объектам, и возвращаем в `diameter_km`.

Диски вокруг узлов, а не свободная кластеризация: это и гарантирует ограничение на диаметр, и сразу даёт привязку к транспорту.

*Допущение:* фактический диаметр может превысить `radius_km` на величину до `2 × r_local`. Считаем честно и показываем в карточке.

## 7. Guard против мисрезолва — обязателен

Координат в ответах Tutu нет, поэтому сверяем по названию и региону.

1. Для каждого города известны `name` и `subject` из `data/cities_ru.json`.
2. После любого `search_*` сравниваем `meta.to.name` и `meta.to.region` с ожидаемыми.
3. Расхождение по региону → **результат отбрасываем полностью**, пишем `warning` и строку в `misresolve_log`, кластер помечаем недостижимым.

Сравнение региона — вхождение подстроки с нормализацией: «Ярославская область» против «городской округ Ярославль, Ярославская область».

`also_named` не проверяем — его не бывает. Полное имя («Ростов Великий», а не «Ростов») передаём всегда.

## 8. Ингредиенты

Полный словарь с тегами, классами Wikidata и измеренной плотностью — в `ingredients.yaml`.

Ключевое: категории неравноценны в сотни раз (храмы 370 на область, водопады 0). Метку плотности показывать в меню обязательно, иначе пользователь соберёт несуществующую комбинацию.

---

## 9. Скоринг значимости

```
significance = 3*has_wikidata + 2*has_wikipedia + 2*has_start_date
             + 1*has_name + min(len(tags)/5, 2)
```

Тег `wikidata` заполнен у 4,4 % объектов, `heritage` — у 0,2 %. Одиночным признаком ранжирования быть не могут.

`start_date` грязный: `"after 1600"`, `"1725..1836"`. Нужен парсер интервалов.

«Древний» = `start_date_to < порог` **или** наличие в Wikidata с `P571` раньше порога (по России 282 таких храма).

## 10. Продуктовые решения (зафиксированы)

| Вопрос | Решение |
|---|---|
| Ингредиенты | меню ~20 карточек + поле «другое» с подсказками |
| Даты | N дней в пределах месяца, проверяем по одному окну в неделю |
| Бюджет | по умолчанию только транспорт, переключатель «всё», всегда раскладка |
| Форма поездки | переезд с вещами, ночёвка в каждой точке |
| Порядок городов | система, по географии |
| Радиус | общий диаметр набора, дефолт 100 км, ползунок со счётчиком |
| Выдача | карта + карточки рядом, топ-5 с ценами |
| Неполные совпадения | отдельный блок «почти подходит» |
| Непродаваемые места | показывать с пометкой «дальше своим ходом» |
| Недостижимые после origin | остаются серыми, с причиной |
| Объекты в кластере | все на карте, топ в карточке |
| Ожидание | результаты по мере готовности (SSE) |
| Часы работы | три состояния; веб-поиск лениво, только после клика |
| Обратное плечо | если нет — искать возврат из другого города маршрута |
| Пассажиры | поля «взрослые» и «дети» |
| Фолбэк | кэш последних цен с отметкой времени |
| Шеринг | ссылка на результат |
| LLM | только там, где детерминированный код не справляется |
| Стек | Python (FastAPI + SQLite) + React + MapLibre, Docker на VPS |

MapLibre, а не Leaflet: на карте тысячи точек, Leaflet рисует каждую как DOM-элемент.
