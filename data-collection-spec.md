Что и как собирать перед тем, как конвейер заработает. Написано для кодового чата: скрипты живут в `ingest/`, запускаются на VPS, где есть настоящая сеть.

Все числа и предупреждения ниже — из полевой проверки 2026-08-19 (`tutu-mcp-field-test.md`), а не из документации. Документация в нескольких местах расходится с реальностью, и эти места отмечены отдельно.

## 0. Как вообще ходить в Tutu MCP

Endpoint `https://mcp.tutu.ru/mcp`, JSON-RPC 2.0 поверх POST. Авторизация не нужна, заголовок `mcp-session-id` сервер не требует.

```
POST /mcp
Content-Type: application/json
Accept: application/json, text/event-stream

{"jsonrpc":"2.0","id":1,"method":"tools/call",
 "params":{"name":"search_multitransport","arguments":{...}}}
```

Ответ приходит либо как `application/json`, либо как SSE с префиксом `data: ` — парсер должен уметь оба варианта.

Перед первым вызовом — `initialize` с `protocolVersion: "2025-06-18"`.

### Вежливость к API

Это API спонсора хакатона, и перебор по тысяче городов — заметная нагрузка.

- Не больше **4–5 параллельных запросов**. На проверке шесть проходили, но запаса нет.
- Между волнами пауза. Реестр узлов строится один раз, спешить некуда.
- Результат каждого вызова **кэшировать в БД сразу**, до обработки. Повторный прогон не должен снова дёргать API.
- В `clientInfo.name` писать осмысленное имя команды, а не `probe`.

## D1. Реестр продаваемых узлов

**Зачем.** Без него нельзя ни привязать кластер POI к транспорту, ни включить guard. Это единственный датасет, который блокирует всё остальное.

**Почему нельзя взять готовым.** `tutu://geo` — заглушка: 2 города, 30 остановок, полей всего два (`geo_id`, `name`), координат нет вообще. Справочника узлов не существует ни в каком виде.

### Кандидаты

Файл `data/cities_ru.json` — 1 134 города России с координатами, населением и субъектом (источник: `pensnarik/russian-cities` на GitHub). Покрытие: все 85 субъектов, 268 городов в радиусе 400 км от Москвы, 398 в радиусе 600 км.

**Население — плохой предиктор продаваемости.** Проверено: Выкса (53 тыс.) не продаётся, Ростов Великий (30 тыс.) продаётся. Эвристики не работают, нужен честный перебор.

Порядок волн:
1. 268 городов в радиусе 400 км от Москвы — покрывает демо-сценарии
2. Все города свыше 100 тыс. населения — 175 штук
3. Остальные

### Проба

```python
search_multitransport(
    origin="Москва",
    destination=<город>,
    departure_date=<будний день через 3-4 недели>,
    adults=1,
    page_size=1,
)
```

Дата в будущем на 3–4 недели: слишком близкая дата даёт ложные нули из-за распроданности, слишком далёкая — из-за неоткрытых продаж.

### Как читать ответ

Продаваемость определяется **не** числом вариантов, а полем `meta.modes_summary` и списком `meta.unavailable`.

```jsonc
"unavailable": [
  {"mode":"avia","reason":"no_route",
   "detail":"avia requires avia_id for destination, but the geo lookup did not return one"},
  {"mode":"railway","reason":"no_route",
   "detail":"railway requires railway_id for destination"}
],
"modes_summary": {"bus":{"count":0,...},"etrain":{"count":0,...}}
```

Это Выкса. Город резолвится корректно, но у него нет `avia_id` и `railway_id`, а автобусов и электричек нет физически. Итог — `sellable_modes = ''`.

Правила записи:

| Условие | Значение |
|---|---|
| `modes_summary[m].count > 0` | режим `m` продаётся |
| `unavailable[].reason == "no_route"` + упоминание `*_id` | у города нет идентификатора этого режима |
| все режимы пусты | город непродаваем, но **не удаляем** — он идёт в режим «дальше своим ходом» |

**Непродаваемые города нужны так же, как продаваемые.** Владимир → Суздаль (35 км) не продаётся, а Суздаль — один из самых востребованных пунктов Золотого кольца. Он должен быть в базе с флагом «добираться самостоятельно».

### Guard против мисрезолва — обязателен в самом пробере

Подтверждено дважды на живых данных:

| Запрос | Резолвится в |
|---|---|
| «Великий Новгород» | **Санкт-Петербург** |
| «Ростов» | **Ростов-на-Дону** |
| «Ростов Великий» | Ростов Великий ✓ |

Оба раза вернулась полноценная выдача с ценами и без единого предупреждения. **Поле `also_named`, которое документация обещает при омонимии, не пришло ни разу.** Полагаться на него нельзя.

Проверка после каждого вызова:

```python
if normalize(meta.to.region) != normalize(expected_region):
    mark_misresolve(city, got=meta.to.name, got_region=meta.to.region)
    return NOT_SELLABLE   # результат выбрасываем целиком
```

`expected_region` берём из `cities_ru.json` (поле `subject`). Совпадение по названию региона проверять с нормализацией: «Ярославская область» против «городской округ Ярославль, Ярославская область» — вхождение подстроки, а не равенство.

Все случаи расхождения писать в отдельную таблицу `misresolve_log`. Это одновременно и защита, и материал для доклада жюри: «мы нашли системную ошибку в вашем API» — сильный ход.

### Схема на выходе

```sql
hub(
  name, subject, lat, lon, population,
  tutu_geo_id,          -- meta.to.geo_id
  resolved_name,        -- meta.to.name, для аудита
  resolved_region,
  sellable_modes,       -- 'railway,bus,etrain' или ''
  min_price_from_moscow,
  latency_ms,
  checked_at
)
```

Оценка объёма: волна 1 — 268 вызовов, при concurrency 4 и медиане 3 с это около 4 минут.

## D2. Матрица перегонов

**Зачем.** Продукт строит маршрут «переезд с вещами» между двумя городами. Перегон между малыми городами массово не продаётся, и знать об этом надо заранее, а не в момент показа карточки.

### Что перебирать

Только пары **продаваемых** узлов (из D1) на расстоянии ≤ 150 км друг от друга. Пары непродаваемых бессмысленны — туда всё равно своим ходом.

Приоритет: пары, где по данным OSM высокая плотность объектов. Пара двух пустых городов не нужна никому.

### Асимметрия — проверять обе стороны

Проверено: Тверь → Торжок продаётся (электричка 276 ₽), **Торжок → Москва даёт ноль**. Прямого сообщения нет, а пересадку через Тверь `search_multitransport` не строит — составные маршруты сервер не собирает вообще.

Отсюда два следствия:

1. Перегон `A→B` и перегон `B→A` — **разные записи**. Наличие одного ничего не говорит о другом.
2. Обратное плечо до origin надо проверять отдельно для **каждого** города маршрута. Если из последнего города возврата нет, продукт должен предложить возврат из предыдущего.

### Известные результаты (для регрессионного теста)

Продаются:

| Перегон | От | Режимы |
|---|---|---|
| Тверь → Торжок | 276 ₽ | etrain |
| Рязань → Коломна | 306 ₽ | etrain |
| Тула → Калуга | 479 ₽ | railway, etrain |
| Ярославль → Ростов Великий | 659 ₽ | railway, etrain |
| Орёл → Тула | 847 ₽ | railway, bus, etrain |
| Кострома → Ярославль | 1 179 ₽ | railway, etrain |
| Ярославль → Иваново | 1 180 ₽ | railway, bus |

Не продаются: Владимир → Суздаль (35 км), Муром → Выкса (40 км), Нижний Новгород → Городец (60 км), Ростов Великий → Переславль-Залесский (65 км), Череповец → Кириллов (100 км), Иваново → Кострома (105 км).

Если пробер выдаёт другое — сначала подозревать пробер, а не изменившиеся данные.

## D3. POI из OSM

**Источник:** Geofabrik, `russia-latest.osm.pbf`, около 4 ГБ. Парсинг локально через `pyosmium`.

**Overpass для этого не годится.** Замерено: 2 слота на IP, 114 секунд на двенадцать счётчиков по одному региону, 504 на национальный запрос по массовому тегу, и полная остановка после нескольких запросов подряд. Overpass оставить только для точечных проверок.

Что вытаскивать — см. `ingredients.yaml`, там теги, правила разбора `start_date` и формула значимости.

Отдельно нужно вытащить **границы регионов** (`admin_level=4`) — они дают `expected_region` для guard'а и привязку POI к субъекту.

Ожидаемый порядок величин: на среднюю область около 550 объектов по базовому набору из четырёх категорий. По всей стране с расширенным набором — десятки тысяч.

## D4. Wikidata

**Зачем.** Слагаемое в формуле значимости и единственный способ фильтровать «древность» помимо `start_date` из OSM.

**Ограничение.** Тег `wikidata` в OSM заполнен у 4,4 % объектов. Матчинг по этому тегу покрывает мало — нужен матчинг по координатам с радиусом порядка 100 м.

**Объём.** Церквей в России с заполненной `P571` раньше 1600 года — **282 объекта на всю страну**. Это не тысячи, планировать надо исходя из сотен.

SPARQL через `query.wikidata.org/sparql`. Простой `COUNT` выполнялся 22 секунды — запросы разбивать по классам и по регионам, не тянуть всё одним.

```sparql
SELECT ?x ?xLabel ?coord ?inception WHERE {
  ?x wdt:P31/wdt:P279* wd:Q16970 ;
     wdt:P17 wd:Q159 ;
     wdt:P625 ?coord .
  OPTIONAL { ?x wdt:P571 ?inception }
  SERVICE wikibase:label { bd:serviceParam wikibase:language "ru,en" }
}
```

Классы для остальных категорий — в `ingredients.yaml`, поле `wikidata_classes`.

## D5. Прогрев кэша и фолбэк для демо

Четыре эталонных сценария × четыре окна дат в октябре 2026 × состав «1 взрослый» и «2 взрослых».

Пишется в `route_cache` и `hotel_cache` с отметкой времени. При недоступности API на выступлении отдаём последние известные цены с явной пометкой «данные на такое-то время» — это решение уже принято.

Эталон №1 для регрессии (проверен живьём 2026-08-19, даты 9–11 октября 2026, 1 взрослый):

| Плечо | Цена |
|---|---|
| Москва → Ярославль | 1 035 ₽ |
| Ярославль → Ростов Великий | 659 ₽ |
| Ростов Великий → Москва | 898 ₽ |
| Отель Ярославль, 1 ночь | от 750 ₽ |
| Отель Ростов Великий, 1 ночь | от 1 000 ₽ |
| **Итого** | **4 342 ₽** |

## Ловушки, на которых легко потерять полдня

1. **Цена отеля — это `stay_total`, а не цена за ночь.** Поле `price_basis` говорит об этом явно, объект `stay` содержит `nights`. Умножать на число ночей нельзя — получите двойной счёт.

2. **Per-mode soft-fail молчит.** Если один вид транспорта отвалился, `search_multitransport` вернёт остальные и не сообщит об этом внятно — цена по маршруту окажется занижена или завышена относительно соседей, а ранжирование соврёт. Всегда сверять `modes_requested` с `modes_summary` и логировать расхождение.

3. **Электрички с ценой 0 ₽.** Встречались в выдаче Ярославль → Ростов-на-Дону. Нулевую цену считать отсутствующей, а не бесплатной.

4. **Латентность до 26,7 секунды.** Худший замер — Владимир → Муром: 26,7 с и ноль результатов. Тайм-аут ставить не меньше 30 с, иначе будете терять честные ответы. Быстрый пустой ответ (0,1–0,8 с) почти всегда означает «у назначения нет нужного `*_id`».

5. **Regex по `name` в Overpass не проходит.** Дважды не уложился в 45 секунд. Фильтрация по названию — только офлайн, после выгрузки.

6. **Полное имя города обязательно.** «Ростов» ведёт в Ростов-на-Дону. Всегда передавать то имя, которое стоит в OSM и в `cities_ru.json`.
