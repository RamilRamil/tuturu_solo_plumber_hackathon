# Инвариант

Продаваемость — свойство **направленного ребра** `(origin_hub → dest_hub)`,
хранится в таблице `leg`. `A→B` и `B→A` — разные записи. `hub.sellable_modes`
допустим только как **производное** (`reachable_from_any`), с явной пометкой,
что это не свойство направления.

# Почему это одностороння дверь

Модель данных ключуется на «узел» повсеместно. Если продаваемость записать как
атрибут узла, а потом окажется (а это уже доказано данными), что она — свойство
ребра, менять придётся схему, ингест, ранжирование и UI разом.

Доказательство из живых данных: Тверь → Торжок = 276 ₽ (etrain),
Торжок → Москва = 0. Составные маршруты сервер не строит.

# Что считать нарушением

- Таблица без `leg` либо `leg` без направленности (PK не включает обе стороны).
- `/api/places` в фазе 1 отдаёт `"sellable": true` как свойство узла →
  после origin сереет не хвост, а масса.
- Обратное плечо проверяется одним вызовом на маршрут, а не для каждого города.

# Как проверяю

Схема БД: есть ли `leg(origin_hub, dest_hub, ..., PK(origin_hub, dest_hub, date_probed))`.
Воркер C: тянет ли продаваемость плеча из `leg`, а не из `hub`.
Связано с [phase-boundary](phase-boundary.md) (серые карточки).
